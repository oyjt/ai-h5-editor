# ud-design 产品方案：需求、架构与技术选型

> 状态：阶段 1 已在本仓库落地（见 README「ud-design 阶段 1」）。本文由在线方案文档导出，技术选型已同步为 Vue 3 + Ant Design Token + Tailwind/UnoCSS + Style Dictionary。依据列里「文章」表示来自参考文章，「推导」和「假设」为本方案自己的判断。

最后更新：2026-11-19

## 背景与参考

ud-design 的目标是复刻 TaoDesign 的核心思路：设计师用对话驱动、在自研画布上直接得到可交互、符合规范、能一键转成代码的设计稿。TaoDesign 是淘宝设计团队的内部工具，以下事实全部来自卡兹克《时隔3年，我重新入职淘宝当了一天设计师》一文，未经第二来源核实。

**TaoDesign 走过三个阶段，前两个都被放弃了。**

| 阶段 | 做法 | 放弃原因 |
|---|---|---|
| 1. 对话式网站 | 说需求，AI 生成纯 HTML，交给开发 | 模型能力不足；淘宝业务知识和系统太复杂，灌入上下文后仍有大量人工修改，设计师改起来费劲 |
| 2. Figma / MasterGo 插件 | 把生成结果塞回传统画布 | 画布自定义性差，解决不了后续与开发走查还原的问题 |
| 3. 自研 TaoDesign | AI 与自研画布结合，容纳十几年设计经验、规范和业务知识 | 目标是设计师的交付物就是最终上线的产品，没有实现损耗 |

**文章中可确认的产品能力：**

- 全局快捷键（Command+Shift+空格）唤起输入框，任务进度显示在屏幕顶部的“灵动岛”里。
- 选风格模板（如手淘的首页、搜索结果、详情、直播、订单），写一段 Prompt 或直接丢入 PRD，选模型，生成可点击、可滑动、带动效的设计稿。
- 画布可像 Sketch / Figma 一样手动编辑；也可框选后丢回对话，让 AI 修改。
- 资源库一键换图、换文字，图片框随尺寸自适应；还能让 AI 联网搜索并替换为真实商品的图、字、价格。
- 风格蒸馏：把 200 多个知识库、存量设计稿源文件、组件 Token、历史改版 PRD 蒸馏成 AI 可调用的风格库和 Skill；规范迭代时二次蒸馏，系统左右对比并高亮差异，由人确认后发布。
- 数字用户：基于真实行为数据，支持一对一访谈、六人圆桌（完整报告约 15 到 20 分钟）和调研快问（约 2 分钟出结论）；另有“页面数据预测”Skill，预测信息识别度、体验问题和点击分布。
- 实时设计：连接代码库，通过 MCP 把设计稿变成可开发版本；技术同学称频道页约 5 分钟可还原并上线走查。
- 一个会话里可以逐页扩展并自动沿用已调好的规范；可引用另一个会话的内容；可同时并行多个任务；有分支功能，用于拓展浮层、二级页、深色模式、骨架屏、缺省态；支持折叠屏等多设备适配。
- 提示词优先级最高，其次才是模板和知识库。作者一次丢入 6 个模板加大段细节，结果规范被覆盖、产出不可用；建议新人把 Prompt 写粗，一页一页做。
- 约 15% 的用户是产品经理；团队方向是从“交付设计”转为“交付设计的能力”。

## ud-design 的定位与设计原则

**定位：** 面向企业内部设计团队的 AI 原生设计工作台，用 UI / 产品原型设计作为首个场景，交付物是可交互的高保真原型，并能一键转成可开发代码。

**原则：**

1. 交付物即产品：设计稿的数据结构要能无损映射到代码，不再有“还原设计稿”这一步。
2. AI 与画布同源：对话和手动编辑操作同一份文档，两种方式随时切换。
3. 规范是资产：规范、组件和历史经验被工程化为风格库，可版本化、可对比、可发布。
4. 创意与规范可调：Prompt 优先还是规范优先做成显式模式，避免新人用细节覆盖规范。
5. 人负责判断：所有自动流程在关键节点留出人工确认，如风格库发布、代码上线。

## 第一部分 需求文档

ud-design 首期要让设计师和产品经理在一个工作台里完成“描述需求、生成可交互原型、画布微调、规范校验、转成代码”的闭环，并且生成结果默认遵守团队规范。

### 1.1 用户与场景

| 角色 | 核心诉求 | 典型场景 |
|---|---|---|
| 设计师 | 把执行性工作交给 AI，把时间花在思辨和判断上 | 接到一句话需求，当天出完整链路方案并评审 |
| 产品经理 | 自己出可点击 demo，改文案、加现成模块 | 用 PRD 直接生成原型，拿去给业务汇报 |
| 规范 / 设计系统管理员 | 让规范可被 AI 调用，并随迭代更新 | 导入历史设计稿和 Token，蒸馏风格库，审核发布 |
| 前端开发 | 设计稿无损转成代码，减少走查 | 通过 MCP 拉取设计稿并还原页面，扫码真机走查 |
| 用研 | 缺少用研资源的需求也能得到初步结论 | 用数字用户快速访谈，预测页面点击与问题 |

### 1.2 核心用户旅程

1. 设计师按快捷键唤起输入框，选风格库，写一句话需求或丢入 PRD，选模型。
2. 系统先搜索风格库，生成第一个页面，任务进度显示在悬浮岛里。
3. 设计师在同一会话里逐页扩展，如店铺页、详情页、下单页，系统自动沿用已确认的规范。
4. 对不满意的区域，直接在画布上双击修改，或框选后丢回对话让 AI 改。
5. 用资源库一键换成目标行业的真实商品图和文案。
6. 用分支补全浮层、二级页、深色模式、骨架屏和缺省态。
7. 校验规范、预测点击表现，在全屏预览里走通交互。
8. 分享给评审人，通过代码连接把设计稿转成可开发版本，扫码上手机走查。

| 维度 | 要求 | 建议目标 |
|---|---|---|

| 安全 | 业务数据和设计稿不出企业边界；代码库访问最小权限 | 模型调用走企业网关，访问全程审计 |

### 1.5 范围

**首期包含：** FR-01 至 FR-20 中所有 P0 与 P1，FR-23 至 FR-27；以 UI / 产品原型设计为唯一场景。

**首期不包含：** 数字用户与页面数据预测（FR-21、FR-22），联网换真实内容（FR-14），折叠屏等多设备预览（FR-16），电商营销图和海报设计，桌面客户端（Web 稳定后再评估）和移动端。

### 1.6 验收标准

1. 给定一句话需求和一个风格库，5 分钟内生成包含至少 3 个页面、可点击跳转的原型，且规范校验无阻断项。
2. 在画布上双击修改文字和间距，与对话修改作用于同一份文档，撤销和重做可跨两种方式。
3. 框选任意区域并提出修改，只有该区域及其依赖元素发生变化。
4. 导入一套历史设计稿和 Token 后，能蒸馏出风格库；发布前必须有人工确认记录。
5. 选定一个页面，通过 MCP 生成的代码能在移动端预览中还原，视觉差异走查项不超过 5 处（建议目标）。

### 1.7 已确认事项

- 首期定位为内部工具：FR-26 按企业 SSO + 角色设计权限，模型走统一网关，暂不做对外计费和多租户。
- 首个风格库采用 Ant Design 规范，以其 Design Token 作为底座；自有业务规范后续通过二次蒸馏叠加。
- 首期先做 Web：快捷键唤起面板和任务悬浮岛都在浏览器内实现，跨应用的全局唤起和系统级悬浮岛留给后续桌面壳。
- 样式使用 Tailwind CSS，Token 由 Style Dictionary 编译，Ant Design 的 Token 作为输入源。

## 第二部分 架构设计方案

ud-design 的核心是一份结构化的设计文档（Design DSL）：画布、AI 和代码生成都读写它，因此不存在“把生成结果再还原成设计稿”或“把设计稿再还原成代码”的损耗，这正是 TaoDesign 前两个阶段失败后得出的结论。

### 2.1 总体分层

客户端负责交互，三个核心服务分别管 AI 执行、设计文档和风格库，能力层提供模型、资源和代码生成，底层是通用的存储与队列。

> 图示：ud-design 总体架构 · 5 层（见在线文档，此处未导出）

高亮的设计文档服务是整个系统的中心：Agent 只对它提交补丁，画布只对它读写，代码生成只从它读取。

### 2.2 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 设计稿格式 | 自有 Design DSL：组件树 + Token 引用 + 自动布局 + 交互声明 | 纯 HTML 难以人工修改，Figma 画布难以自定义，两者都无法直接对接代码 |
| 画布渲染 | 画面（Artboard）用 DOM 渲染，外层画布自研相机和命中检测 | 原型需要真实的点击、滑动和动效；DOM 渲染也最接近最终代码 |
| AI 改稿方式 | Agent 输出对 DSL 的结构化补丁，而不是重写整页 | 支持框选局部修改、撤销重做、回放，也能与手动编辑并存 |
| 规范注入 | 检索风格库注入上下文，校验器在提交前兜底 | 只靠提示词容易被用户细节覆盖，校验器保证规范可执行 |
| 任务执行 | 异步任务 + 事件流，每个任务独立 | 支持多会话并行和悬浮岛进度展示 |
| 转代码 | 直接从 DSL 生成，同时通过 MCP 暴露设计数据 | DSL 已含结构和 Token，比从像素或图层反推更准确 |

### 2.3 Agent 运行时

Agent 的一次执行按固定流程走，任何一步失败都会回到规划或交给人处理。

1. 理解意图：解析 Prompt 或 PRD，识别页面类型和业务场景。
2. 检索规范：从风格库取出对应模板、组件、Token 和规则。
3. 规划：拆成页面清单和每页的结构，先给出计划再动手。
4. 执行：调用工具创建页面、修改节点、替换资源。
5. 校验：用规范校验器检查间距、圆角、颜色、组件使用，自动修正能修的项。
6. 提交：把补丁写入设计文档，推送事件，悬浮岛显示完成。

**Agent 工具集：**

| 工具 | 作用 |
|---|---|
| create_page | 按模板和结构创建画面 |
| patch_nodes | 对指定节点应用补丁，框选修改走此工具 |
| apply_style | 套用风格库的组件和 Token |
| search_assets | 在资源库中检索图片和文案 |
| validate_spec | 运行规范校验，返回问题清单 |
| export_code | 触发转代码，生成预览构建 |

**提示词优先级：** 规范优先模式下，顺序为系统规则、风格库规范、模板、用户 Prompt；创意优先模式下，用户 Prompt 最高。任何模式下，只要用户 Prompt 覆盖了规范项，都会在任务结果里列出“规范偏离清单”。

### 2.4 数据模型

| 实体 | 说明 | 关键字段 |
|---|---|---|
| Workspace | 团队空间，管理成员和风格库 | id、成员、角色、默认风格库 |
| Session | 一次对话，含多个任务 | id、所属空间、标题、引用的其他会话 |
| Task | 一次 Agent 执行 | id、会话、输入、模型、风格库版本、状态、事件日志 |
| Document | 画布文档，一个会话对应一个 | id、画面列表、当前版本、分支 |
| Artboard | 一个页面或状态 | id、设备尺寸、根节点、所属分支 |
| Node | 设计节点 | id、类型、属性、Token 引用、布局、交互、子节点 |
| StyleLibrary | 风格库的一个版本 | id、名称、版本号、状态、发布人、来源知识库 |
| Token / Component | 规范原子和组件 | 名称、取值或结构、所属风格库版本 |
| Asset | 图片和文案资源 | id、类型、行业标签、来源 |

Node 的布局统一用自动布局（类似 flex）描述，而不是绝对坐标，这样画面尺寸变化时内容自适应，也能直接映射到前端代码。

### 2.5 风格库蒸馏管线

1. 导入：上传设计稿源文件、组件 Token、历史 PRD 和规范文档。
2. 解析：把源文件转成统一的节点结构，抽取 Token 和组件。
3. 提炼：归纳页面模式、组件用法和显式规则（如圆角、间距倍数）。
4. 入库：结构化数据存关系库，语义内容建向量索引。
5. 生成 Skill 草案：为每类页面生成可被 Agent 调用的说明和检索入口。
6. 对比：与上一版左右对比，高亮新增、修改和删除。
7. 人工确认：规范管理员逐项确认；未确认的项不会发布。
8. 发布：生成新版本号，旧版本保留，任务记录所用版本。

### 2.6 设计转代码与实时设计

设计转代码由两部分组成：**代码生成器**把 DSL 转成前端组件，**MCP 服务**把设计数据开放给开发侧的 Agent。

| MCP 工具 | 作用 |
|---|---|
| get_design | 读取某个画面或节点的结构 |
| get_tokens | 读取所用的 Token 与组件映射 |
| get_assets | 下载画面用到的图片资源 |
| export_component | 生成指定节点的前端组件 |
| push_preview | 在代码库分支上生成预览构建，返回二维码 |

文章指出，真正的难点是把设计意图对接到背后复杂的业务系统，而不是像素转代码。因此 DSL 里给节点预留“数据绑定”声明，用来说明某个组件对应哪个业务接口和字段，由团队在风格库里维护映射（该设计为 ud-design 的扩展，文章未描述具体做法）。

### 2.7 安全与权限

- 所有模型调用经过企业模型网关，按空间配置可用模型、限流和成本归集。
- 设计稿和知识库按空间隔离，跨空间引用需要显式授权。
- 代码库令牌最小权限：只允许读取目标目录、向预览分支写入，不允许直接合并。
- 风格库发布、代码推送、联网检索白名单都有审批和审计日志。

### 2.8 评估与可观测

- 每次任务保存输入、风格库版本、模型、补丁序列和校验结果，可回放。
- 统计规范校验通过率、人工修改比例、任务耗时和失败原因，用来评估风格库和提示词的质量。

## 第三部分 技术选型方案

全栈统一用 TypeScript：客户端、服务端、DSL、校验器和代码生成器共享同一套类型定义，这是保证“设计稿即代码输入”的最低成本做法。以下均为建议，未做基准测试，首期原型阶段需要用真实数据验证画布性能和生成质量。

### 3.1 选型总表

| 层 | 选型 | 主要备选 | 理由 |
|---|---|---|---|
| 桌面壳 | 首期纯 Web，无桌面壳 | 后续用 Electron 或 Tauri 封装 | 先验证画布和 Agent 链路；快捷键用浏览器内唤起面板，悬浮岛做页内浮层。需要系统级快捷键和置顶窗口时，再用同一套前端封装桌面壳 |
| 前端框架 | Vue 3 + TypeScript + Vite（在 ai-h5-editor 上改造） | React 18（重写前端） | 已确认在现有 ai-h5-editor（Vue 3）上改造，复用编辑器、组件注册表、撤销重做和预览发布，不重写；生成代码的目标先是 Vue，需要对接 React 业务线时再给代码生成器增加 React 目标 |
| 画布引擎 | 自研：CSS Transform 相机 + 空间索引（R-tree）做命中检测 | tldraw、Konva、Fabric | 画面需要真实 DOM 和交互动效，通用 Canvas 库做不到；文章中团队也是自研画布以获得完全可控 |
| 前端状态 | Pinia（沿用现有 Store，补丁合并为一条撤销记录） | Redux Toolkit、Yjs | Immer 直接产出补丁，可与 Agent 补丁统一；多人协作期再引入 Yjs |
| 样式与 Token | Tailwind CSS + Style Dictionary | CSS 变量 + 自有 Token 编译器 | Style Dictionary 把风格库 Token 编译成 Tailwind 主题和 CSS 变量，生成的代码直接用 Tailwind 类名，无需映射层 |
| 组件规范 | Ant Design 5（设计器界面与首个风格库） | 自有组件库、shadcn/ui | 内部工具场景下规范成熟、组件齐全；其 Token 可直接导入 Style Dictionary，与 Tailwind 主题打通 |
| 服务端 | Node.js + Fastify + TypeScript | NestJS、Go | 与客户端共享类型；Fastify 轻量，插件化好 |
| Agent 运行时 | 自研轻量循环 + Vercel AI SDK 适配多模型 | LangGraph、Claude Agent SDK | 多模型是硬需求；自研循环更容易接入补丁、校验和事件流；Agent SDK 绑定单一厂商 |
| 工具协议 | MCP（官方 TypeScript SDK） | 自定义 HTTP | 文章中设计转代码即走 MCP，生态里开发侧 Agent 都能直接接入 |
| 主数据库 | PostgreSQL（JSONB 存节点树） | MySQL、MongoDB | 事务、JSONB 和 pgvector 一个库解决；节点树按画面分片存储 |
| 向量检索 | pgvector（首期） | Qdrant、Milvus | 减少组件；风格库规模大或检索压力高时再拆出 |
| 对象存储 | S3 兼容（私有化可用 MinIO） | 厂商 OSS | 图片、设计稿源文件、构建产物 |
| 队列与缓存 | Redis + BullMQ | RabbitMQ、Temporal | 任务量中等，BullMQ 足够；需要长流程编排时再评估 Temporal |
| 实时通道 | WebSocket（任务事件、悬浮岛进度） | SSE | 后续协作和多端同步可复用 |
| 设计稿解析 | Figma REST API、Sketch 文件解析、PSD 解析库 | 仅支持 Figma | 文章提到团队有存量 Sketch 与 Figma / MasterGo 设计稿，首期先覆盖 Figma 与 Sketch |
| 规范校验器 | 自研规则引擎（JSON 规则 + TypeScript 谓词） | 现成 lint 库 | 规则要读 DSL 与 Token，且需给出自动修正动作 |
| 代码生成 | Vue 单文件组件模板 + Prettier（React 目标后续用 ts-morph） | 模板字符串 | 基于语法树生成，便于做增量更新和保持代码风格 |
| 预览构建 | 容器沙箱（gVisor）里跑 Vite 构建，生成预览地址和二维码 | 本机构建 | 隔离不可信代码，支持扫码真机走查 |
| 认证 | OIDC / 企业 SSO | 自建账号 | 企业内部工具，复用现有身份体系 |
| 可观测 | OpenTelemetry + Langfuse（模型调用追踪） | 自建日志 | 任务回放和提示词评估需要完整的模型调用记录 |
| 部署 | Docker + Kubernetes | 单机 Compose | 预览沙箱和任务队列需要弹性伸缩；原型阶段可先用 Compose |

### 3.2 模型接入

- 通过模型网关统一接入 Claude、GPT、Gemini、Qwen 等，按任务类型路由：规划与校验用推理强的模型，批量填充和换文案用便宜的模型。
- 文章提到 TaoDesign 提供免费的顶级模型，这依赖企业自身的额度和网关；ud-design 把成本归集到空间，并支持各团队自带密钥。
- 所有请求记录模型名、版本和提示词摘要，方便复现和对比不同模型的规范通过率。

### 3.3 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 生成稿覆盖规范（文章作者踩过的坑） | 产出无法在企业内使用 | 规范优先模式作为新手默认；校验器兜底；输出偏离清单 |
| 自研画布性能不足 | 页面多时卡顿，体验差 | 视口外节点虚拟化；DOM 画面按需渲染；原型阶段先压测 |
| 风格库质量差 | 生成效果依赖它，错误会放大 | 蒸馏后必须人工确认；记录版本；用规范通过率评估 |
| 设计稿源文件解析不全 | 导入后丢失图层或 Token | 首期只承诺 Figma 和 Sketch；对不支持的元素给出报告 |
| 业务系统对接复杂 | 转出的代码仍需大量手工对接 | 先保证 UI 层无损；数据绑定声明作为独立迭代 |
| 模型成本不可控 | 并行任务多时费用上升 | 按空间配额；缓存检索结果；任务前给出成本预估 |
